# Pipeline 与 Hybrid 离线现场部署指南

## 一、部署架构

```text
客户端 -> Router:8002 -> 32.15.75.232:16002 (API-1) ─┐
                      ├> 32.15.75.232:16003 (API-2) ─┤ 都在 232 上
                      ├> 32.15.75.232:18001 (API-3) ─┤
                      └> 32.15.75.232:18002 (API-4) ─┘
                           每个 API: pipeline -> 本地 PDF-Extract-Kit-1.0
                                     hybrid-http-client -> 外部 VLM
外部 VLM(本 Compose 不创建):
  mineru-vlm-1  32.15.75.232:6002
  mineru-vlm-2  32.15.75.232:6003
  mineru-vlm-3  32.15.84.31:8001
  mineru-vlm-4  32.15.84.31:8002
```

API 端口必须避开同机 VLM 和 Router 的端口:232 上 VLM-1/VLM-2 已占用 6002/6003,
Router 占用 8002,因此四个 API 使用 16002/16003/18001/18002。`env.multi.example`
已经按这个形态填好,直接复制即可。

现场是无网络的麒麟 ARM/NPU 环境。任何模型下载、Git 拉取和镜像构建都必须在进场前完成。

当前形态是 232 单机承载 Router/Ops 和四个 API 节点,因此该主机使用 `all`:

```text
32.15.75.232: MINERU_DEPLOY_ROLE=all, MINERU_API_NODE_IDS=1,2,3,4
```

如果改成"一台机器跑 Router、两台机器跑 API"的旧形态,则 API 主机用 `api` 并把
`MINERU_API_NODE_IDS` 改成该主机实际启动的节点,Router 主机用 `router`。
该文件的 `MINERU_ROUTER_UPSTREAM_URLS_JSON` 已按四个 API 的地址填好,
每个 API 节点都要配置它实际使用的 `VLM_N_IP/VLM_N_PORT`:API-1/2 用 232 的 6002/6003,
API-3/4 用 31 的 8001/8002。也就是说 232 上的 `env.multi` 里四项都要填
(维护的是全部四个 VLM 的可达性),而不是只填本机那两个。

同一台主机上的多个 API 节点必须绑定互不相同的 NPU 卡号
(`PIPELINE_NPU_ID`、`PIPELINE_2_NPU_ID`、`PIPELINE_3_NPU_ID`、`PIPELINE_4_NPU_ID`),
并且要避开本机 VLM 正在使用的卡;启动前先 `npu-smi info` 确认。

后续新增节点时，先在对应 API 主机用 `MINERU_API_NODE_IDS` 启动已在 Compose 中定义的节点，
再在 Router/Ops 的「配置中心」编辑 `MINERU_ROUTER_UPSTREAM_URLS_JSON`，预览确认只重建
Router 后点击应用。跨主机自动创建 Docker 容器不由 Router/Ops 代办，新增主机仍需先完成
镜像、模型、NPU 映射和 API 服务部署。

## 二、进场前交付物检查

```text
docker/multi/
├── artifacts/mineru-pipeline-models-3.4.2.tar.gz
├── artifacts/mineru-pipeline-models-3.4.2.tar.gz.sha256
├── images/mineru-env-v1.0.tar.gz
├── images/mineru-code-v3.4.2-ops-ui20.tar.gz
├── compose-multi.yaml
├── env.multi.example
├── mineru.pipeline.json
├── start-multi.sh
└── test.pdf（或其他小型测试 PDF）
```

来源必须明确：

- Pipeline 模型归档：联网 WSL 使用 `prepare-pipeline-models.sh` 生成；
- `mineru-code`：联网 ARM/NPU 服务器从 GitHub 拉取相同代码版本后构建；
- `mineru-env`：同一服务器使用与现场 CANN/驱动配套的 Ascend PyTorch 基础镜像构建并完成 NPU 验证；
- 外部 VLM：现场已有或另行部署，本 Compose 不创建 VLM。

## 三、校验并解压模型

```bash
cd /path/to/docker/multi/artifacts
sha256sum -c mineru-pipeline-models-3.4.2.tar.gz.sha256

cd ..
```

## 四、配置

```bash
cp env.multi.example env.multi
```

重点修改：

```dotenv
MINERU_DEPLOY_ROLE=all
MINERU_API_NODE_IDS=1,2,3,4

MINERU_ENV_IMAGE=mineru-env:v1.0
MINERU_CODE_IMAGE=mineru-code:v3.4.2-ops-ui20
PIPELINE_MODEL_HOST_PATH=./models/PDF-Extract-Kit-1.0
PIPELINE_CONFIG_HOST_PATH=./mineru.pipeline.json
MINERU_MODEL_SOURCE=local

VLM_1_IP=32.15.75.232
VLM_1_PORT=6002
VLM_2_IP=32.15.75.232
VLM_2_PORT=6003
VLM_3_IP=32.15.84.31
VLM_3_PORT=8001
VLM_4_IP=32.15.84.31
VLM_4_PORT=8002
```

模板里的 API 端口已按 232 单机四节点填好(16002/16003/18001/18002)。
如果现场其他服务占用这些端口,再改成空闲端口,并同步更新
`MINERU_ROUTER_UPSTREAM_URLS_JSON` 和 `MINERU_API_NODE_<N>_URL`。

`VLM_N_IP` 不能填写 `127.0.0.1` 或 `localhost`。四个 VLM 地址都要填:留空不会报错,
但容器内会回落到 `127.0.0.1:30000` 并静默连不上 VLM;而 `check` 只在填了 IP 时
才做连通性检查,留空时依然显示检查通过。`MINERU_VLM_MODEL` 只用于控制台展示,
实际模型名由 `mineru_vl_utils` 请求 VLM 的 `/v1/models` 自动获取,因此每个 VLM
端点必须恰好只暴露一个模型。

设备模式分两种：

- Pipeline 使用 NPU:`mineru-env` 必须包含与现场 CANN 匹配的 `torch_npu`,并设置 `MINERU_DEVICE_MODE=npu`。
- `compose-multi.yaml` 会手工映射指定的 `/dev/davinciN`、公共管理节点以及宿主机 Ascend 驱动目录;启动前必须确认这些路径存在。
- 232 单机启动 4 个 API 时,`PIPELINE_NPU_ID`/`PIPELINE_2_NPU_ID`/`PIPELINE_3_NPU_ID`/`PIPELINE_4_NPU_ID` 必须是四张不同的卡,并避开 VLM 占用的卡;先执行 `npu-smi info` 确认。

## 五、导入镜像

```bash
./start-multi.sh import-images
docker image inspect mineru-env:v1.0 --format '{{.Architecture}}'
docker image inspect mineru-code:v3.4.2-ops-ui20 --format '{{.Architecture}}'
```

如果本次交付使用 UI21，将上面的代码标签和归档文件名同步替换为
`mineru-code:v3.4.2-ops-ui21` 与 `mineru-code-v3.4.2-ops-ui21.tar.gz`。

现场应输出 `arm64`。如果输出 `amd64`，镜像架构错误，不能继续启动。

## 六、检查并启动

```bash
./start-multi.sh check
./start-multi.sh start
./start-multi.sh status
```

`check` 会验证：

1. Compose 和 `env.multi`；
2. 两个镜像标签；
3. 七组 Pipeline 模型；
4. `mineru.pipeline.json` 和容器内模型挂载；
5. API 容器到外部 VLM 的 `/v1/models` 连通性。

## 七、测试 Pipeline 和 Hybrid

```bash
./start-multi.sh test /path/to/test.pdf
```

也可以分别调用：

```bash
curl -f -X POST http://127.0.0.1:8002/file_parse \
  -F "files=@/path/to/test.pdf" \
  -F "backend=pipeline"

curl -f -X POST http://127.0.0.1:8002/file_parse \
  -F "files=@/path/to/test.pdf" \
  -F "backend=hybrid-http-client"
```

第一次请求会加载模型，耗时明显高于后续请求。健康检查成功不等于模型链路成功，必须完成上述解析请求。

## 八、运维控制台日常操作

- 首次使用前在 `env.multi` 设置非空的 `MINERU_OPS_AUTH_TOKEN`；否则控制台是只读模式。
- 「配置中心」的 `MINERU_ROUTER_UPSTREAM_URLS_JSON` 可增删已部署 API 节点。预览时如果只改该项，受影响服务应只有 Router；API 业务参数则需要在对应 API 主机应用。
- 「任务」页的「清理过期任务」只清理超过 `MINERU_OPS_TASK_RETENTION_DAYS` 的控制台缓存；仍被批次记录引用的任务会保留。批次删除会同时清理关联任务明细和页级耗时记录。
- 批量测试脚本无对应进程或超过 `MINERU_OPS_BATCH_MAX_RUNTIME_SECONDS` 时，后台看门狗会将记录标记为 `interrupted`，随后可以删除记录。它不会取消已经提交到远程 API 的任务。

## 八、修改配置后重建容器

模型挂载、环境变量或设备映射变化后执行：

```bash
./start-multi.sh stop
./start-multi.sh check
./start-multi.sh start
```

## 九、故障定位

```bash
docker logs -f mineru-api-1
docker logs -f mineru-router
npu-smi info
```

- `缺少 Pipeline 模型`：解压层级错误或归档不完整；
- `容器内缺少模型`：检查挂载路径，或确认归档已解引用符号链接；
- VLM `/v1/models` 失败：检查 VLM 地址、监听地址、防火墙和模型名；
- NPU 不可用：检查环境镜像、CANN/torch_npu 版本、设备节点和驱动挂载；
- `Read-only file system`：保持输出目录为 `/var/lib/mineru/output`。
