# 双环境 PDF 解析性能与 MinerU 输出能力综合报告

## 一、测试目的

本报告以 MinerU 为唯一主评估对象，对比公司 NVIDIA Tesla T4 环境和现场昇腾 910B3 环境在同一批 PDF 上的解析性能，并结合 MinerU 对公式、表格、图文版面和结构化结果的处理目标，分析现场昇腾环境的慢速及超时问题。

重点分析以下内容：

1. 两套环境处理相同 PDF 时的总耗时和吞吐差异；
2. VLM 请求的平均耗时、P50、P95 和长尾请求差异；
3. 现场页面超时的实际影响，以及提高超时后慢页的真实处理时间；
4. 不同 PDF 内容类型对处理速度和输出任务复杂度的影响；
5. MinerU 与 RAGFlow 在公式、表格、图文版面和结构化结果方面的提取效果差异；
6. MinerU 官方仓库中与 NPU 稳定性、性能和超时相关的公开问题，能否对现场现象形成外部佐证。

本报告的定量结论全部来自 MinerU 两套环境的同条件测试。关于 MinerU 输出能力的表述，重点是本次解析任务实际需要的公式、表格、版面和结构化结果能力；没有把未完成的盲测质量统计伪装成精确准确率。

### 2.2 时间口径

- **MinerU 总用时**：Excel 中记录的整本任务用时，包含页面处理、排队、超时等待以及失败页处理产生的时间。
- **去除超时页总用时**：Excel 中记录的扣除超时等待后的估算值，不等同于所有页面完整成功的重新实测结果。
- **VLM 请求耗时**：Excel 中记录的平均请求耗时、P50、P95 和最慢请求，单位为秒。
- **吞吐**：按 `页数 ÷ 总用时（分钟）` 计算，是任务级吞吐，不等同于成功页面的纯推理吞吐。

### 2.3 本报告以 MinerU 为主

本次资料的核心问题是：在同一套 PDF、模型和业务参数下，现场昇腾环境运行 MinerU 为什么明显变慢，以及这种慢速是否会影响公式、表格和复杂图文页面的完整处理。MinerU 的输出链路与本次文档类型直接对应：

- 公式识别结果可以进入 Markdown/LaTeX 等结构化文本，便于继续编辑、检索和复核；
- 表格识别结果可以保留表格结构，而不只是把页面降级为连续 OCR 文本；
- 图文版面、标题层级、段落和图片信息可以进入 Markdown、Middle JSON、Content List 等结构化结果；
- 对扫描版教材、技术图、矩阵、公式和密集表格，MinerU 的目标是同时保留内容和版面关系，而不是只统计“任务完成时间”。

### 2.4 MinerU 与 RAGFlow 的提取效果判断

#### 2.4.1 本次技术 PDF 场景下的结论

在本次技术 PDF 的交付目标下，MinerU 的提取效果整体优于 RAGFlow，更符合后续编辑、检索、复核和再利用的要求。这里的“更好”不是指单纯任务完成得更快，而是指输出对原始 PDF 中公式、表格、阅读顺序和版面关系的保留更完整、更容易直接使用。

具体表现可以从以下几个方面理解：

| 对比维度 | MinerU | RAGFlow 在本次场景中的局限 | 对交付结果的影响 |
| --- | --- | --- | --- |
| 公式、矩阵和 LaTeX | 面向 PDF 解析保留公式结构，可输出 Markdown/LaTeX 等可编辑表达 | RAGFlow 的核心目标是知识库导入、切分和检索，公式结构是否完整保留取决于实际解析器、版本和配置 | MinerU 更适合教材、论文、工程技术文档中的公式复用和人工校对 |
| 表格 | 以表格结构为目标，可进入 Markdown/HTML 或中间结构化结果 | 表格在进入知识库切分后可能被展平为文本，合并单元格、行列关系和表头层级不一定保留 | MinerU 更适合需要继续编辑、导出或核对表格的场景 |
| 阅读顺序和版面 | 同时处理标题、段落、图片、图注、公式和表格的页面关系 | RAGFlow 更关注分块后的检索文本，原始版面关系通常不是首要输出目标 | MinerU 更适合保留原文结构和还原页面语义 |
| 图片和图文混排 | 可保留图片资源及其在文档结构中的位置，并与 Markdown/JSON 结果关联 | RAGFlow 是否保留图片、图注和相邻正文关系取决于具体解析链路 | MinerU 更适合技术图、曲线图和图文混排教材 |
| 结构化结果 | 提供 Markdown、Middle JSON、Content List 等多种结果，便于下游加工 | RAGFlow 的主要结果是知识库分块和检索索引，不等同于完整文档还原 | MinerU 更适合作为文档提取、转换和质量复核的前置工具 |

因此，本报告对本次五本 PDF 的功能性判断是：**MinerU 的提取效果比 RAGFlow 更符合需求，尤其在公式、矩阵、表格、图文版面和结构化文档输出方面更有优势。** RAGFlow 更适合作为后续知识库、切分、召回和问答系统使用，而不是本次技术 PDF 的高保真提取结果基准。

#### 2.4.2 结论边界

上述判断基于本次文档的输出目标、MinerU 的结果形态以及 RAGFlow 的产品定位，不等同于在完全相同版本、模型、解析器和参数下完成了逐页准确率盲测。现有资料没有足够的 RAGFlow 中间结果、公式/表格人工标注和完成页数记录，因此本文不虚构“准确率提高多少”或“每类页面提升多少”的数字；但这不影响对本次交付目标的工具选择判断：需要高保真保留公式、表格、版面和结构化结果时，优先使用 MinerU，RAGFlow 放在后续知识库处理环节。

## 六、现场慢页真实处理时间

### 6.1 单页复测结果

现场提高单页超时时长后，对 Excel 中明确列出的 14 个页码进行了单页测试：

| PDF | 页码 | 单页真实用时 |

| 空气动力学 | 161 | 31 min |
| 空气动力学 | 185 | 25 min |
| 空气动力学 | 207 | 0.5 min |
| 空气动力学 | 318 | 33 min |
| 空气动力学 | 325 | 61 min |
| 空气动力学 | 400 | 32 min |
| 空气动力学 | 448 | 31 min |
| 动机心理学 | 153 | 29 min |
| 动机心理学 | 176 | 29 min |
| 高等代数 | 171 | 31 min |
| 高等代数 | 226 | 28 min |
| 高等代数 | 249 | 29 min |
| 高等代数 | 250 | 30 min |
| 高等代数 | 253 | 27 min |

14 个明确列出的复测页中：

- 13 页耗时在 **25–61 分钟**之间；
- 最慢为空气动力学第 325 页，耗时 **61 分钟**；
- 空气动力学第 207 页耗时 **0.5 分钟**，与其他复测页差异很大，属于当前数据中的例外。

原始单页超时阈值为 600 秒，即 10 分钟：

- 25 分钟约为 1500 秒，是 600 秒的 2.5 倍；
- 61 分钟约为 3660 秒，是 600 秒的 6.1 倍；
- 单纯将阈值从 600 秒提高到 1200 秒，仍不足以覆盖上述大多数慢页。

这说明 600 秒会提前截断一批最终可能完成的页面，并且这些页面通常不是只超时几十秒，而是需要数倍于原阈值的时间。如果希望覆盖本次列出的最慢页，理论上至少需要约 3660 秒。但将常规生产配置设置到这么大，会长期占用 VLM/API 并发槽，使其他请求排队，不适合作为默认生产配置。

### 6.2 超时现象的工程含义

现有数据支持以下判断：

1. 现场的 600 秒超时会在部分页面最终完成之前触发跳页或失败记录；
2. 超时等待是现场总耗时增加的重要因素，但现场扣除超时等待后仍然明显慢于公司；
3. 对慢页进行单独重试并使用较长请求时长，适合用于定位页面真实处理时间；
4. 常规生产任务应保留有限超时和明确失败策略，不建议直接把默认超时时间设置为无限大；
5. 如果底层 HTTP 请求没有真正取消，任务层面的失败记录可能与服务端后台仍在处理的状态不一致，这需要结合 API、Router 和 VLM 的取消语义及运行日志进一步确认。

## 七、MinerU 输出任务与 PDF 内容复杂度

### 7.1 影印、图文公式类文档是 MinerU 的高负载场景

高等代数和空气动力学包含扫描正文、矩阵、公式、曲线和技术图。两本 PDF 的现场平均 VLM 请求耗时约为公司环境的 3 倍，P95 约为公司的 3.36–4.26 倍，最慢请求约为公司的 8.93–9.16 倍。

这类页面通常需要完成整页视觉识别、公式结构恢复、图文布局理解和较长的结构化输出。对本次任务而言，输出不能只停留在纯文本 OCR：矩阵、行列式、积分、上下标、公式编号、曲线和图注需要尽可能保留关系，表格需要尽可能保留行列结构，标题和正文还要进入可继续处理的 Markdown、Middle JSON 或 Content List。因此，这些页面既是 MinerU 的价值所在，也是 VLM 推理和结构化生成的高负载场景，更容易放大单页处理的长尾耗时。

### 7.2 原生 PDF、纯文本或文本占比较高的文档

解忧杂货铺、动机心理学和长三角论文的平均请求倍率为 1.55–2.04 倍，低于两本影印图文公式类文档，但现场仍慢于公司。

这说明文档内容复杂度会影响差距大小，但不是现场性能差异的唯一原因。即使页面相对简单，现场的平均请求耗时仍然更高。对原生 PDF，MinerU 仍然需要把正文、标题、图片、公式和表格组织成可复用的结构化结果；“页面更容易处理”不等于输出目标退化为简单文本。

### 7.3 页面复杂度不是唯一解释

矩阵、公式、曲线、技术示意图和密集表格可能增加视觉理解、结构恢复和输出生成量并放大长尾，但复杂页面并非只出现在现场慢页中。现有数据可以说明这些内容是 MinerU 的高负载输出任务和潜在长尾放大因素，不能据此断定某一类页面在脱离运行环境后必然失败。

## 八、官方 Issue 对昇腾环境风险的外部佐证

本节只用于说明现场现象并非完全孤立，不把其他 Issue 的测试数字与本报告的 MinerU 数字混合计算，也不把不同版本、不同模型和不同后端的 Issue 直接当作现场环境的复现实验。

### 8.1 Issue #5361：昇腾 910B3 长时间运行后的稳定性退化

官方 Issue [#5361](https://github.com/opendatalab/MinerU/issues/5361) 标题为“华为昇腾 NPU 910B3 部署 MinerU 使用 pipeline 模式报错 507035（ACL_ERROR_RT_VECTOR_CORE_EXCEPTION）”。问题描述中，4 卡 × 64 GB 的 910B3 环境持续 48 小时解析 PDF/DOCX 后，解析成功率随时间出现不可逆下降；日志出现 `ACL_ERROR_RT_VECTOR_CORE_EXCEPTION`、`AclrtSynchronizeDeviceWithTimeout` 和运行时错误码 `507035`。Issue 给出的复现条件包括 24 个实例、24 个并发线程和长时间持续调用 MinerU 接口。

该 Issue 不能证明本次现场单卡一定发生了同一个 ACL 错误，因为本次报告的任务规模、实例数量和持续时间不同；但它提供了与现场问题方向一致的官方工程背景：昇腾 910B3 + MinerU + 昇腾推理运行时在持续负载下可能出现稳定性退化、底层设备异常和成功率下降。Issue 讨论还指出，NPU 内存碎片、同卡多实例资源竞争以及大显存设备的缓存清理策略可能成为长期运行风险，说明“显存容量更大”不能直接等同于“MinerU 解析一定更快或更稳定”。

### 8.2 Issue #5322：NPU/vLLM 吞吐不一定随节点数线性增加

官方 Issue [#5322](https://github.com/opendatalab/MinerU/issues/5322) 标题为“阿里 NPU 部署 MinerU 使用 vlm-engine 模式巨慢无比问题”。其中记录单卡 NPU 约 `0.4 page/s`，扩展到 8 个节点后反而约 `0.24 page/s`；对照 NVIDIA 3090，单卡和多卡约为 `1.2–1.5 page/s`。这不是昇腾 910B3 的直接测试，也不是本报告的同版本复现，但它支持一个重要的工程判断：NPU、推理框架、并发方式和实例布局之间存在明显耦合，增加节点或实例数量不保证吞吐提升，甚至可能下降。

这与本报告现场“单页请求平均更慢、P95 和最慢请求长尾明显放大、增加等待时间仍不能恢复到公司 T4 水平”的现象具有方向上的一致性。它不能替代现场的逐请求 profiling，但增强了“问题可能来自昇腾配套推理运行时和部署形态，而不只是 PDF 内容”的判断。

### 8.3 Issue #5293：超时问题需要区分运行时路径，不能简单归咎于 PDF

官方 Issue [#5293](https://github.com/opendatalab/MinerU/issues/5293) 的主体是 Windows managed parse-server 在 PDF 转图阶段固定 300 秒超时，正文同时指出相关的 Linux + Ascend NPU + pipeline 问题属于不同场景。该 Issue 对本报告的价值不是证明昇腾变慢，而是提供一个边界：PDF 渲染进程池、服务端运行上下文和设备运行时都可能造成超时，不能把所有超时简单解释成 PDF 文件本身异常。

因此，本报告对现场慢页采用更谨慎的归因：页面中的公式、矩阵、表格和技术图会增加 MinerU 结构化输出负载；但五本 PDF 的常规请求、P50、P95、最慢请求和单页复测结果共同表明，现场昇腾环境的整体推理速度和长尾延迟是主要背景。官方 Issue 提供外部工程佐证，但不替代现场版本、模型和部署参数的直接 profiling。

## 九、综合分析

### 9.1 总体速度差异

五本 PDF 的 MinerU 结果中，现场总用时和平均 VLM 请求耗时均高于公司。现场原始总用时为 443 分钟，公司为 166 分钟；现场总体吞吐为 3.03 页/min，公司为 8.08 页/min。

### 9.2 文档类型和长尾

影印、图文公式类文档的差距最大；原生 PDF 或文本占比较高的文档差距相对较小，但仍然存在。页面结构会改变请求处理量，现场环境的长尾延迟则进一步放大了这一差异。

### 9.3 超时等待的影响

现场原始总用时与扣除超时等待后的估算相差 140 分钟。去除这部分等待后，现场仍比公司慢 1.83 倍，说明性能差异同时来自常规请求耗时和慢页长尾，而不是单一的超时配置。

### 9.4 MinerU 输出能力与现场慢速的关系

本次 PDF 集合不是简单的纯文本 OCR 任务，而是包含扫描教材、矩阵、公式、曲线、技术图、图片和不同类型表格的混合文档。MinerU 的目标输出包括可阅读 Markdown、公式结构、表格结构、图片和中间 JSON 等内容，这些能力正是本次技术资料后续编辑、检索和复用所需要的。换言之，不能为了追求一个更低的“页/分钟”数字，把公式、表格和版面关系降级为不可复用的纯文本结果。

现场慢速的实际代价不仅是任务完成时间更长，还包括：

1. 复杂公式和表格页面更容易进入长尾，触发 600 秒超时；
2. 超时后需要异常页重试，影响结果完整性和人工复核成本；
3. 现场同一批 PDF 出现跳过页，而公司 T4 全部完成，说明昇腾环境的慢速已经影响 MinerU 的可用交付结果，而不仅是性能指标变化。

## 十、结论

1. 五本 PDF 按 Excel 口径共 1342 页。MinerU 公司 T4 环境累计用时 166 分钟，现场昇腾环境累计用时 443 分钟，现场为公司的 **2.67 倍**，整体吞吐约为公司的 **37.5%**。
2. 按 Excel 中扣除超时等待后的估算值，现场基础耗时约 303 分钟，仍为公司环境的 **1.83 倍**，说明超时等待不是全部性能差异的来源。
3. 五本 PDF 的现场平均 VLM 请求耗时均高于公司，倍率为 **1.55–3.09 倍**；P95 倍率为 **2.15–4.26 倍**。高等代数和空气动力学的最慢请求约为公司的 **8.93–9.16 倍**，现场长尾问题明显。
4. 14 个明确列出的现场单页复测中，13 页耗时为 **25–61 分钟**，最慢页耗时 61 分钟。原始 600 秒阈值会提前截断一批最终可能完成的页面，单纯改为 1200 秒仍不足以覆盖大多数复测慢页。
5. 矩阵、公式、曲线和技术图可能增加 VLM 处理量并放大长尾，但页面结构不是现场慢页现象的唯一解释；现场差异更符合昇腾 910B3 及其配套软件栈在该工作负载上整体处理较慢、且尾部延迟更高的表现。
6. 本次五本技术 PDF 的提取效果判断是：**MinerU 整体优于 RAGFlow，更符合本项目需求。** 优势主要体现在公式和矩阵可编辑表达、表格行列结构、标题与段落阅读顺序、图片和图注关系，以及 Markdown、Middle JSON、Content List 等结构化结果。RAGFlow 更适合在提取完成后承担知识库切分、检索和问答，不适合作为本次高保真 PDF 提取效果的替代基准。当前资料没有形成统一版本和参数下的逐页准确率盲测，因此本文不虚构具体提升百分比。
7. MinerU 官方 Issue #5361 记录了昇腾 910B3 长时间高负载解析中成功率下降和 `ACL_ERROR_RT_VECTOR_CORE_EXCEPTION`/`507035`；Issue #5322 记录了 NPU + vLLM 解析速度偏低且扩展节点后吞吐反而下降；Issue #5293 则提醒超时还可能与服务运行上下文有关。它们不能直接替代现场 profiling，但共同说明昇腾 NPU MinerU 部署存在需要重点验证的性能、稳定性和运行时风险。
