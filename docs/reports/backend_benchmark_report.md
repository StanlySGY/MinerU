# MinerU Backend 性能测试报告

## 1. 测试背景

MinerU 是一个文档解析工具，支持三种后端（Backend）模式：

| Backend | 说明 | 计算位置 |
|---|---|---|
| `pipeline` | 传统多模型流水线 | 全部本地 CPU |
| `vlm-http-client` | 纯大模型端到端 | 远程 VLM Server（NPU） |
| `hybrid-http-client` | 小模型 + 大模型协作 | 本地 CPU + 远程 VLM |

本报告对三种后端在相同测试集上的处理性能进行对比测试，为生产环境部署选型提供数据支撑。

## 2. 测试环境

| 项目 | 配置 |

| API Server | CPU 服务器（ARM），端口 18000 |

| VLM 推理框架 | vLLM |

- 每个 Backend 独立测试，测试间等待 5 秒让 VLM 释放资源

## 6. 分析与结论

### 6.1 Pipeline 最快的原因

- 全部在本地 CPU 执行，无网络开销
- 专用模型（PP-DocLayoutV2、PaddleOCR、MFR）各自处理单一任务，效率高
- 无 VLM 推理的 GPU/NPU 资源竞争

### 6.2 VLM 最慢的原因

- 所有任务都通过 HTTP 发到远程 VLM Server，网络延迟叠加
- VLM 需要同时完成布局检测、文字识别、公式识别、表格识别，计算量大
- 3 个并发请求同时竞争同一个 VLM Server，显存和 KV Cache 资源不足导致处理速度退化

### 6.3 Hybrid 居中的原因

- 布局检测在本地完成（快），减少了 VLM 的计算量
- VLM 只需在已知区域内提取内容，比纯 VLM 的工作量少
- 但仍有网络开销，所以不如纯 Pipeline

### 6.4 并发对 VLM 的影响

从日志观察到，VLM Server 在处理 3 个并发文档时，处理速度从 5s/it 退化到 45s/it（9 倍退化）。这是因为：

- vLLM 的 KV Cache 被多个请求瓜分
- 每个请求分到的显存减少，batch size 被迫降低
- 请求排队等待推理资源

## 7. 部署建议

| 场景 | 推荐 Backend | 理由 |
|---|---|---|
| 追求处理速度 | pipeline | 纯本地最快，无网络开销 |
| 需要图片/图表理解 | vlm-http-client | VLM 唯一支持的能力 |
| 需要多语言支持 | hybrid-http-client | Pipeline 小模型支持多语言 |
| 平衡速度与精度 | hybrid-http-client | 比纯 VLM 快 33% |
| 高并发批量处理 | pipeline | 本地并行，无 VLM 瓶颈 |

## 8. 性能优化建议

1. **降低 VLM 并发**：将 `MINERU_API_MAX_CONCURRENT_REQUESTS` 从 3 调为 1，避免 VLM 资源竞争
2. **增加 VLM 实例**：多起几个 VLM Server，用 Router 分散负载
3. **增大处理窗口**：将 `MINERU_PROCESSING_WINDOW_SIZE` 从 32 调为 64，减少 HTTP 请求次数
4. **使用本地模型**：如果不需要图片理解，用 pipeline 最快
